현재 작업본은 `C:\frontend`의 `develop`이며 백엔드는 `C:\backend`의 `test`다. 백엔드 API 계약1.9·데이터 형식1.0·DB v11·출력 template_v10을 기준으로 사용한다. 계약 원본은 `C:\backend\contracts.md`, 검사 근거는 `C:\backend\task_backend.md`다. 이 프론트 저장소에 계약 문서 사본을 새로 생성하지 않았으며 원격 공유·병합은 별도다.

```powershell
Set-Location C:\frontend
npm run dev -- --host 127.0.0.1
```

- 백엔드 연동: `http://localhost:5173/`. `/api` 요청은 Vite 프록시가 `VITE_API_URL` 또는 기본 `http://127.0.0.1:8000`으로 전달하며 소유자 쿠키를 유지한다. API 오류를 가상 성공으로 바꾸지 않는다.

## 실제 백엔드 연결 고정 (2026-10-01)

현재 서비스에서는 고정 가짜 자료·점검·초안·승인·PDF 대체 결과를 사용하지 않는다. 첫 접속은 작업 시작 화면이며, 서버 연결에 실패하면 오류를 표시한다. 이전 `session-demo-standalone` 저장값은 복원하지 않는다. `mockBackend.ts`의 예시 자료/회사 정보/고정 사진은 제거했고, 미연결 사진 수집은 명시적인 오류를 반환한다. 실제 회사 자료와 백엔드 DB에 명시적으로 등록한 `[시연]` 자료는 계속 구분해 조회한다.

개발 서버의 `/api`는 `VITE_API_URL` 또는 기본 `http://127.0.0.1:8000`으로 전달된다. 작업 시작 응답의 작성 조건을 그대로 반영하므로 서버 기본 필드 때문에 곧바로 ‘저장 필요’가 뜨지 않는다. 초안/승인 화면은 실제 서버 문서가 있어야 열린다.

검증: TypeScript/Vite 빌드·수정 파일 ESLint, 메모리 훅 검사9건(첫 접속·작업 시작 실패·옛 가짜 세션·복원 실패·실제 응답·선택/설정/업로드 실패·예시 제거) 통과. 실행 중인 프론트에서 실제 서버 세션 생성과 등록 자료21개 표시를 확인했다. 유료 AI 호출0회이며 생성·승인·출력 전체의 새 실제 모델 검증은 이 프론트 수정 범위가 아니다.

## 현재 연결 범위 (2026-09-29)

S01·S02·S03 화면은 백엔드의 루트 `contracts.md` 계약 1.5에 맞춰 **자료 선택 → AI 점검·초안 → 문구 편집·저장 → 내용 검증 → 경고 확인 → PDF 배치 검사 → 최종 승인 → PDF 다운로드**에 연결한다. 작성 조건 저장, 첨부 삭제와 작업 종료도 지원한다. 업로드만으로 자료를 자동 선택하지 않는다. 조회는 소유자 쿠키를 사용하며 새로고침 시 같은 탭의 작업 ID를 복원한다.

- 자료 연결: `src/api/sources.ts`, `src/hooks/useSources.ts`, `SourceSelectionView.tsx`. AI 연결: `src/api/aiWorkflow.ts`, `src/hooks/useAiWorkflow.ts`, `AiWorkflowPanel.tsx`.
- 시연 자료를 쓰려면 시작 화면의 ‘시연 자료 사용’을 체크하고, 백엔드에 `DEMO_MODE=true`를 설정한다. `demo=true`로 만든 세션만 시연 자료를 선택할 수 있다. 실제 제공 자료와 시연 자료는 목록에서 구분한다.
- 파일당 10MB·작업당 10개를 안내하며 TXT/MD/PDF/DOCX/PPTX/JPG/PNG를 지원한다. 최종 허용 여부는 서버가 검사한다. 일부 읽기·실패·네트워크 오류를 성공으로 바꾸지 않는다.
- 업로드 응답 유실 시 같은 파일과 같은 요청 키로 재시도한다. 새로고침 후에도 같은 파일을 다시 선택하면 중복 방지 키를 재사용한다. 선택 충돌은 최신 목록을 다시 읽고 사용자에게 재선택을 안내한다.
- AI 점검은 사실·근거 구간·보완 사항·추천 분량을 표시한다. 생성 가능 여부는 서버 응답을 따르며, 확인 체크 후에만 초안을 요청한다. 이 확인이 누락/상충 해결이나 최종 승인을 대신하지 않는다. 자료·작성 조건 변경 시 이전 점검 확인을 폐기하며, 미저장 조건·읽기 진행 중에는 점검/생성을 막는다.
- AI 접수 응답 유실은 같은 키로 재전송하고, 상태 조회 실패는 GET으로 다시 확인한다. 새로고침은 진행 중 Job/저장된 결과를 조회하며 자동으로 새 AI 요청을 보내지 않는다. 자동 조회는 최대 120회이며 실패하거나 오래 걸리면 수동 상태 확인을 안내한다. 초안 실패 후에는 점검부터 다시 진행한다.
- 브라우저 저장소에는 세션/읽기/AI 작업·점검 ID와 입력 버전 및 재전송용 해시·키만 보관한다. 원문·사진·AI 결과 본문은 저장하지 않는다. 사용자 확인은 새로고침 후 다시 받으며 미저장 작성 조건은 사라진다. 초안은 서버에서 복원한다.
- `src/api/publication.ts`, `src/hooks/usePublication.ts`, `DocumentWorkspace.tsx`가 제목·본문·목록 편집과 블록 삭제, 내용 검증·개별 경고 확인·PDF 미리보기·최종 승인·다운로드를 연결한다. 상단 단계 버튼은 초안이 준비되면 별도 S01·S02·S03 화면으로 전환한다. 화면을 오가도 미저장 문구와 진행 중인 작업을 유지한다. 서버에서 허용한 경고만 사유를 입력해 확인하며 필수 문제를 확인 클릭으로 통과시키지 않는다. DOCX는 비활성화 상태다.
- 미저장 편집은 승인·출력을 막고 브라우저 새로고침/종료 시 경고한다. 본문은 브라우저 저장소에 보관하지 않으므로 새로고침하면 미저장 문구는 사라진다. 저장 충돌 시 내 문구를 유지하며 최신 저장본과 비교한 뒤 명시적으로 버릴 수 있다. 저장하면 이전 검사·승인·다운로드는 무효화된다.
- 출력 Job은 새로고침 후 GET으로 재조회한다. 최종 승인 동의·경고 사유·미저장 문구는 복원하지 않는다. 응답 유실 시 같은 요청 키로 재확인하며, 저장·승인·경고 확인 요청은 본문/동의 보호를 위해 현재 화면의 메모리에서만 재시도한다. PDF 재다운로드는 AI를 다시 호출하지 않는다.
- 원문 파일 조회, 실제 LLM 수정안 품질 확인, 사진 선택/의미 검증, DOCX, 초안 생성 후 자료 변경·편집 복귀는 후속이다. 기존 DraftEditorView/ApprovalExportView 시안 모듈은 보존하되 현재 화면에서는 사용하지 않는다.

### S02 수정안 API 연결 (2026-09-29)

- 제목·본문·목록 중 선택한 텍스트 블록 1개에 대해 `POST /documents/{did}/proposals` → Job/Proposal GET → 원문·제안·이유 비교 → `apply` 또는 `reject`를 연결했다. 사용자가 적용하기 전에는 문서를 바꾸지 않는다. 범위 밖 연산·후보 선택이 필요한 응답은 이 화면에서 적용하지 않는다.
- 미저장 편집·진행 중 작업·오래된 버전은 적용을 막는다. 적용 성공 시 새 문서 버전과 기존 검증/승인 무효화를 서버에서 다시 조회한다. 제안 취소는 문서를 바꾸지 않는다.
- 응답 유실은 같은 요청 키로 확인하고, Job 조회 실패는 GET으로 재개한다. 브라우저 저장소에는 작업/수정안 ID·버전·키·요청 문구 해시만 남기고 요청 본문과 문서·제안 본문은 저장하지 않는다. 생성 요청의 접수 응답을 잃은 채 새로고침하면 같은 요청 문구를 재입력해야 한다. 확인 중단 버튼은 서버 작업 취소가 아니며, 새 요청은 별도 처리다. 적용/취소 응답 유실은 동일 키로 재확인할 수 있다.
- **실제 LLM 문구 수정안 코드 연결:** 백엔드 `LlmAgent.propose`는 원문 근거가 연결된 제목·문단·목록 한 블록을 수정한다. 반환된 ID·출처·숫자 토큰을 검사하고, 기존 근거/사실 ID/제목 수준을 유지한다. 구조·사진 수정은 미지원이다. 숫자 검사는 단위·조건의 의미 검증을 대신하지 않으며 적용 뒤 내용 검증이 필요하다. 오류를 mock 성공으로 대체하지 않는다. SDK 대역과 임시 DB의 API 테스트를 통과했고, 실제 LLM 가상 납기 문구 1건의 생성·비교·적용도 확인했다. 전체 자료의 표현 품질과 입력 축소 후 실제 내용 검증은 후속이다.

- 후속 진단에는 허용된 API 응답 상태·미완료 사유·출력 상한만 남기고 원문/모델 본문은 로그에 추가하지 않는다. `max_output_tokens`로 미완료된 응답은 화면에서도 출력 한도 중단으로 구분하며, 자동 재시도나 가짜 검증 성공으로 바꾸지 않는다. 백엔드 관련 테스트 466개 통과. 실제 응답 길이/반복 문제의 확인과 재검증이 남았다.


### 내용 검증 재시험 통과와 빈 페이지 정리 (2026-09-29)

위 실패 기록 이후 백엔드가 검증 응답의 검사 ID 목록을 실제 대상 개수로 제한하고, 대상 밖 ID/불필요한 사실 ID 반복을 생성 스키마에서 제한했다. 검증 설명은 간결하게 요청하며 기존 원문·조건·심각도·승인 기준은 유지한다. 이전 출력 8,000토큰 도달의 정확한 내부 원인을 단정하지 않는다.

- 실제 내용 검증을 각 1회로 제한한 두 시험이 모두 완료됐다. 첫 시험은 출력 340토큰·4쪽 PDF, 빈 페이지 정리 후 시험은 1,416토큰·2쪽 PDF 21,174바이트다. 두 응답 모두 `completed`, `incomplete_reason=null`이었다. 두 호출의 이번 추정 합계는 $0.00202554이며 과거 실패/호출 비용·실제 청구액과 구분한다. 최종 `call_limit`은 배정된 1회를 정상 소진한 상태다.
- 두 번째 모델은 사업 내용의 표현 반복 1개를 warning으로 지적했다. 이를 시연 경고와 함께 개별 확인한 뒤 실제 PDF 배치 검사→명시적 승인→다운로드→동일 바이트 재다운로드까지 통과했다. 후속 편집으로 기존 승인/다운로드가 무효화되는 것도 확인했다. 조건 손실·근거 없는 사실 등 blocker의 차단 정책은 유지한다.
- S02에 **빈 페이지 정리** 버튼을 추가했다. 블록이 전혀 없는 페이지만 사용자가 눌러 제거하며 내용이 있는 페이지와 마지막 한 페이지는 보존한다. 먼저 문구를 저장해야 하고, 변경 중/충돌/미확인 요청이 있으면 사용할 수 없다. 기존 `delete_page` API와 문서 버전·중복 요청 방지를 사용한다. 페이지 정리 뒤에는 내용/PDF 검사와 승인을 다시 해야 한다.
- replay 검사는 원래 문서 복원을 확인한 뒤 빈 페이지가 있을 때 이 버튼을 실행한다. 모의 모드에서는 저장 응답 유실/같은 키 재시도까지 검사하며, 실제 모드는 유료 검증 1회만 수행한다. 시험의 서버 검증 결과는 자기 가상 자료의 `validation-result.json`에 남긴다. 원시 모델 응답·키·쿠키는 남기지 않는다.
- 백엔드는 새 초안의 회사명 제목이 `회사명은 테스트나무입니다.`이고 원문에 `회사명: 테스트나무`가 정확히 있으면 `테스트나무`로 표시한다. 원문 확인 없이 접미사를 제거하지 않으며 기존 저장 문서를 자동 변경하지 않는다. 이번 replay PDF는 이전 저장 제목을 유지한 결과이고, 새 제목 규칙은 백엔드 회귀로 확인했다.
- 확인: 백엔드 관련 **474 passed**, 프론트 TypeScript·수정 TS 파일 ESLint·Vite 배포 빌드 통과. 오프라인 페이지 정리와 실제 최종 흐름은 각각 **9개 검사 묶음** 통과. 최종 PDF 두 쪽을 렌더링해 한글·시연 표시·일반 주문/영업일/특수 주문 조건과 빈 페이지 제거를 확인했다.
- 산출물: 실제 첫 시험 `ddalgi-ai-ui-JBn7KV`, 최종 `ddalgi-ai-ui-49nm16`, 오프라인 정리 `ddalgi-ai-ui-1w44Xs` (사용자 임시 폴더). 최종 PDF는 기능 확인용 가상 자료다. 실제 거산 자료 전체의 생성/검증 품질, 사진 의미 검증·구조 수정·DOCX 등 미완료 항목까지 완료된 것은 아니다.


### 사진 후보 편집과 실제 이미지 검증 (2026-09-29)

S02에서 텍스트 블록을 선택하면 ‘이 블록 뒤에 사진 추가’, 사진/사진 자리를 선택하면 ‘사진 교체 후보 보기’를 사용할 수 있다. 현재 선택한 자료의 실제 사진만 표시하며 적합성 순위가 아니다. 후보를 고르고 ‘선택한 사진 적용’을 눌러야 저장 문서가 바뀐다. 교체 시 이전 설명·근거는 지워지므로 새 사진 설명을 직접 입력하고 ‘문구 저장’ 후 내용/PDF 검사와 최종 승인을 다시 진행한다.
